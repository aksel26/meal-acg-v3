# 직원 휴가 신청 이벤트 및 연동 감사 결과

## 결론

공식 휴가 신청 흐름은 다음과 같음.

```text
/leave-request
  → /api/leave-requests
  → dayoffs(pending) 생성
  → leave_balances.used 즉시 증가
  → approval_requests(pending) 생성
  → 승인자/신청자/관리자 화면 노출
  → 승인 또는 반려
  → 식대·캘린더·근태·통계 화면이 서로 다른 기준으로 반영
```

가장 큰 문제는 **승인 대기 휴가가 이미 확정 휴가처럼 연차와 식대를 차감**한다는 점임. 반려돼도 연차 차감은 복구되지 않음.

## 조치 결과 (2026-07-22)

감사에서 확인한 결함을 다음과 같이 수정함.

- 휴가와 날짜별 결재 요청은 `create_leave_request_atomic`에서 한 트랜잭션으로 생성함. 요청 UUID를 저장해 같은 요청의 재전송도 중복 생성하지 않음.
- 승인·반려·처리 취소는 `resolve_leave_approval_atomic`에서 대상 행을 잠근 뒤 `dayoffs`와 `approval_requests`를 함께 변경함.
- 연차 사용량은 삭제되지 않은 `approved` 휴가만 반영함. `pending` 생성은 차감하지 않고, 승인 취소·승인 후 삭제는 복구하며, 승인된 휴가의 날짜·유형 변경도 이전 값과 새 값의 차이를 재계산함.
- 기존 연차 사용량은 승인 완료 휴가 기준으로 재계산하며, 결재 요청이 없던 과거 휴가에는 가능한 범위에서 연결 결재 행을 보강함.
- 사용자·관리자 수정과 삭제는 원자적 DB 함수로 통일함. 삭제하면 연결 결재 요청도 반려 상태와 삭제 사유로 마감됨.
- 같은 직원의 같은 날짜에 `pending` 또는 `approved` 휴가가 중복 등록되는 것을 DB 트리거로 차단함.
- 사용자 휴가 상세 API는 로그인 후 본인·대상자·지정 승인자·참조자·관리 권한 사용자만 조회할 수 있음.
- 별도 사용자 승인 API와 관리자 직접 승인 API도 공식 결재 요청을 조회한 뒤 동일한 원자적 승인 함수를 사용함.
- 식대 캘린더·식대 통계·사용자 운영 캘린더·관리자 당일 근태·관리자 휴가 통계는 `approved`이면서 삭제되지 않은 휴가만 반영함.
- 공식 휴가 신청 API는 날짜 형식, 종료일 역전, 과거 날짜, 최대 기간, 휴가 유형, 참조자와 요청 UUID를 검증함.
- 휴가 신청 화면에서 같은 조직의 팀장급 이상 승인자를 선택하며, 서버가 조직·직책·본인 선택 여부를 다시 검증함. 조직 구조상 자동 승인자가 있으면 기본값으로 선택함.
- 신청·승인 후 연차, 식대, 휴가, 결재 관련 클라이언트 캐시를 함께 무효화함.

검증은 로컬 OrbStack Supabase에만 마이그레이션을 적용해 수행함. `supabase/tests/leave_request_workflow.sql`에서 대기/승인/반려/취소/수정/삭제에 따른 잔액, 상태 동기화, 승인자 권한, 중복 차단, 멱등성, 부분 실패 롤백과 RPC 실행 권한을 확인함. 원격 또는 운영 DB에는 적용하지 않음.

## 전체 이벤트 순서

| 순서 | 이벤트 | 실제 동작 |
|---:|---|---|
| 1 | 신청 화면 진입 | 휴가 유형을 조회하고 `지각/조퇴`만 제외함. 연차·반차·휴무·하계휴가·무급휴가 등이 표시됨. |
| 2 | 승인자 미리보기 | `/api/users?includeApprover=true`를 호출하지만 현재 저장소에는 대응 API가 없음. 실패는 숨기고 “조직 구조에 따라 자동 결정”으로 표시함. |
| 3 | 신청 버튼 클릭 | 클라이언트에서 직원 ID·휴가 유형·시작일 존재 여부만 검사함. 현재 UI는 사실상 하루만 선택함. |
| 4 | 신청 API 호출 | `POST /api/leave-requests`가 실행됨. 성공 전까지 버튼이 비활성화됨. |
| 5 | 본인 확인 | 서버는 요청 본문의 `memberId`를 무시하고 로그인 세션 ID를 신청자·휴가 대상자로 강제함. |
| 6 | 승인자 결정 | DB의 `get_approver_for_member`가 팀원→팀장, 팀장→본부장, 본부장→대표 순으로 승인자를 결정함. |
| 7 | 휴일 확인 | `holidays` 테이블을 조회하고 주말·공휴일을 제외함. 신청 시 Google API를 직접 호출하지는 않음. |
| 8 | 날짜 분할 | 기간 신청이면 영업일마다 별도 레코드를 만들 준비를 함. |
| 9 | `dayoffs` 생성 | 영업일마다 `approval_status='pending'`인 행을 하나씩 생성함. |
| 10 | 연차 차감 트리거 | 차감 대상 휴가라면 `leave_balances.used`가 **즉시** 1일·0.5일·0.25일 증가함. 승인 상태는 검사하지 않음. |
| 11 | 결재 요청 생성 | 각 `dayoffs` 행마다 `approval_requests` 행을 별도로 생성함. 한 기간 신청도 날짜별 결재 요청으로 분리됨. |
| 12 | 신청 성공 처리 | 신청 내역·휴가 목록 캐시만 무효화하고 완료 토스트 후 대시보드로 이동함. 연차 잔액·식대·대시보드 캘린더 캐시는 직접 무효화하지 않음. |
| 13 | 승인 대기 노출 | 신청자 목록, 승인자 결재함, 조건부 CC 목록에 나타남. 사용자·관리자 캘린더와 근태 화면에도 바로 나타남. |
| 14 | 식대 반영 | 식대 캘린더와 식대 통계는 `rejected`만 제외하므로 `pending`을 휴가로 처리함. 일일 식대 지원금도 미리 차감됨. |
| 15 | 승인 | 승인자 세션과 요청의 `approver_id`를 비교한 뒤 `dayoffs`와 `approval_requests`를 차례로 `approved`로 변경함. |
| 16 | 반려 | 두 레코드를 `rejected`로 변경함. 식대에서는 다음 조회부터 제외되지만 이미 증가한 `leave_balances.used`는 그대로 남음. |
| 17 | 관리자 처리 취소 | 승인·반려 요청을 다시 `pending`으로 돌릴 수 있음. 연차 잔액 변화는 없음. |
| 18 | 휴가 수정 | 날짜·유형·사유·승인자를 `dayoffs`에서 직접 변경할 수 있음. 연결된 결재 요청과 연차 잔액은 재계산되지 않음. |
| 19 | 휴가 삭제 | `dayoffs.is_deleted=true`가 되고 연차 사용량은 감소함. 그러나 연결된 `approval_requests`는 취소되지 않음. |
| 20 | 삭제 후 결재 | 남아 있는 결재 요청을 나중에 승인할 수 있으며, 삭제된 휴가와 승인 요청의 상태가 서로 달라질 수 있음. |

## 상태별 실제 영향

| 상태 | 연차 사용량 | 식대 차감 | 캘린더·근태 노출 | 공식 승인 집계 |
|---|---:|---:|---:|---:|
| `pending` | 차감됨 | 차감됨 | 대부분 노출됨 | 승인 건수에는 제외 |
| `approved` | 이미 차감된 상태 | 차감됨 | 노출됨 | 포함 |
| `rejected` | **차감 유지** | 제외됨 | 여러 화면에서 계속 노출 | 제외 |
| `is_deleted=true` | 차감 취소 | 제외 | 일반 목록에서 제외 | 연결된 결재 요청은 유지 |

## 연동된 부분

확인된 직접 연동:

- 연차 잔액: 신청 즉시 `leave_balances.used` 변경
- 식대 캘린더: 대기·승인 휴가를 근태로 병합
- 식대 지원금: 대기 휴가도 일일 지원금 차감
- 사용자 대시보드·캘린더: 승인 상태 필터 없이 표시
- 사용자 근태·휴가 프로필: 화면마다 승인 필터가 다름
- 관리자 휴가 캘린더: 대기·승인·반려 모두 표시
- 관리자 당일 출근 현황: 대기·반려도 “휴가자”로 집계
- 관리자 휴가 통계: 일부 통계는 삭제·반려까지 포함
- 승인자 결재함·신청 내역·참조 목록
- 관리자 직원 개요: 이 부분만 승인과 대기를 명시적으로 분리함

연결되지 않은 것으로 확인된 부분:

- 자동 Web Push 알림 없음
- 자동 Slack 휴가 알림 없음
- Google Calendar에 휴가 일정 등록 없음
- 급여·정산 테이블로 직접 전파되는 코드 없음
- 전용 휴가 신청 회귀 테스트 없음

Google Calendar는 휴가 일정을 보내는 용도가 아니라, 관리자가 동기화한 공휴일 데이터를 신청일 필터링에 간접 사용함.

## 결함 순위

| 순위 | 결함 | 심각도 | 확신 |
|---:|---|---|---|
| 1 | 대기 휴가가 연차를 즉시 차감하고 반려 후에도 복구되지 않음 | 높음 | 높음 |
| 2 | 대기 휴가가 식대 지원금까지 즉시 차감함 | 높음 | 높음 |
| 3 | `dayoffs`와 `approval_requests` 생성이 트랜잭션이 아니어서 결재 요청 없는 휴가가 남을 수 있음 | 높음 | 높음 |
| 4 | 승인·반려도 두 테이블을 따로 수정하여 동시 처리나 중간 실패 시 상태가 갈릴 수 있음 | 높음 | 높음 |
| 5 | 수정·삭제가 결재 요청과 동기화되지 않고 날짜·유형 변경 시 연차가 재계산되지 않음 | 높음 | 높음 |
| 6 | 동일 날짜 중복 신청을 막는 DB 제약이나 idempotency가 없음 | 중간 | 높음 |
| 7 | 휴가 상세 조회 API에 인증 검사가 없어 UUID를 알면 사유와 관계자 정보를 조회할 수 있음 | 높음 | 높음 |
| 8 | 별도 사용자 승인 API는 지정 승인자인지 확인하지 않고 `approver_id`만 기록함 | 높음 | 높음 |
| 9 | 관리자 직접 승인 경로는 공식 `approval_status`와 `approval_requests`를 갱신하지 않음 | 높음 | 높음 |
| 10 | 날짜 형식·종료일 역전·과거 날짜·휴가 유형 정책 검증이 부족함 | 중간 | 중간 |

## 추론과 확인 한계

- 최초 감사에서 기록한 이벤트와 상태 불일치는 수정 전 소스와 마이그레이션에서 직접 확인한 증거임.
- 중간 DB 오류가 실제 운영에서 발생했다는 증거는 없음. 부분 저장 가능성은 수정 전 순차 쓰기 구조에서 확인함.
- 수정 후 함수와 마이그레이션은 OrbStack 로컬 DB에서 대조하고 SQL 회귀 테스트를 실행함. 원격·운영 DB에는 적용하지 않음.
- 관리자 타입 검사는 통과했으며, 사용자 타입 검사는 이번 범위 밖의 기존 컴포넌트 및 중복 생성 타입 오류로 실패했음.
